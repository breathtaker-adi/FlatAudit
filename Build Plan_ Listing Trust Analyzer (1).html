Build plan: Listing Trust Analyzer

A beginner-friendly, step-by-step path from an empty folder to a finished portfolio project. Tick items off as you go; your progress is saved in this browser.

0% complete

How to start (first 3 days)

  • Day 1: create the GitHub repo, install VS Code and Node.js, and load a “hello world” extension in Chrome.
  • Day 2: save 5 listing pages as local HTML files and open them in the browser to practice reading fields with the console.
  • Day 3: start the 30-listing spreadsheet (15 suspicious, 15 normal) with price, deposit and your reason for each.

Ground rules for a beginner

Working habits

  • Budget 8–10 hours a week; steady beats heroic
  • Commit to Git at the end of every session
  • Build the smallest working thing, then improve it
  • Write a “done when” line before each task

Safety and fairness

  • Only read pages you open yourself; no bulk crawling
  • Check each portal’s Terms of Service first
  • Never store photos or phone numbers
  • Describe signals, never accuse people

Week-by-week plan

Week 0: Setup and warm-up

3–4 days
Learn
  • JavaScript basics: variables, functions, arrays, fetch, async/await, DOM selectors
  • What a content script and a service worker are
Build
  • Create the repo with a README and .gitignore (ignore eval/labels.csv)
  • Make a Manifest V3 extension that shows an alert on any page
  • Save 5 listing pages as HTML into fixtures/
Done when: the extension loads via “Load unpacked” and fixtures open locally.

Week 1: Read a listing

one portal only
Learn
  • document.querySelectorAll, MutationObserver for pages that load content later
  • Why to prefer stable attributes over auto-generated class names
Build
  • Write a parser that returns title, rent, deposit, BHK, locality and image URLs
  • Test the parser against every fixture file with node --test
  • Inject a small badge element using textContent (never innerHTML with page data)
Done when: the badge shows the parsed rent and locality on a live listing you opened.

Week 2: Image fingerprint (dHash)

the trickiest week
Learn
  • dHash: shrink to 9×8 grayscale, compare each pixel with its right neighbor, giving 64 bits
  • Hamming distance: count differing bits; small means similar
  • Gotcha: images from other domains can block canvas pixel reads in a content script, so fetch the image from the background service worker (with host permission) and use createImageBitmap plus OffscreenCanvas
Build
  • Implement dhash() and hamming() in lib/dhash.js
  • Unit-test: same image resized gives distance near 0; different images give a large distance
  • Hash each listing’s first 3 images via the service worker
Done when: two copies of one photo (one resized) match within your threshold and unrelated photos do not.

Week 3: Rule-based signals

pure functions, easy to test
Learn
  • Mean, standard deviation and z-score; why medians resist outliers
Build
  • priceSignal: compare rent to similar listings (same locality and BHK)
  • depositSignal: deposit divided by rent against a local norm
  • phraseSignal: a short list of advance-fee phrases taken from your own labeled examples
  • Each signal returns {fired, reason} so the badge can explain itself
Done when: each signal has tests with at least one fired and one not-fired fixture.

Week 4: Small backend

FastAPI + SQLite
Learn
  • REST endpoints, request validation with Pydantic, CORS basics
Build
  • POST /observe stores hash, rent, locality and BHK (no photos, no contacts)
  • GET /seen?hash=… returns how many listings share a similar hash (linear scan is fine)
  • Add pytest tests and a CORS allowlist for the extension
  • Connect the extension to localhost and show “seen in N listings”
Done when: opening the same photo’s listing twice shows the duplicate count increase.

Week 5: Collect and label data

your most valuable asset
Build
  • Define labels.csv columns: id, locality, BHK, rent, deposit, label, reason
  • Write a one-page labeling guide so labels stay consistent
  • Label about 250 listings; mark any you were unsure about
  • Relabel 20 random rows a few days later to check your own consistency
Done when: you have at least 100 labeled listings (250 is the target) with a mix of both classes.

Week 6: Evaluate honestly

where the project becomes impressive
Learn
  • Precision, recall, confusion matrix, train/test split
Build
  • Run signals over the dataset in evaluate.py
  • Tune thresholds on a training split; report results on the held-out split
  • Do error analysis: list false positives (such as legitimate broker photo reuse) and why they happened
  • Optional: fit a simple logistic regression and keep it only if it beats the rules
Done when: a results table and a short “what failed” section exist.

Week 7: Security hardening

your cybersecurity chapter
Build
  • Write docs/threat-model.md using STRIDE for the extension and API
  • Trim extension permissions to the minimum; set a strict CSP; no remote code
  • Treat all page data as untrusted: validate on the backend, escape on display
  • Add rate limiting; run npm audit and pip-audit
Done when: each threat has a mitigation or a documented accepted risk.

Week 8: Polish and publish

make it easy to review
Build
  • README: what it is, screenshots, setup in under 5 steps, limits and ethics
  • Architecture diagram and a 2-minute demo video
  • Pick a license; confirm no secrets, personal data or private labels are committed
  • Blog post: what worked, what didn’t, and the metrics
Done when: a stranger can clone the repo and run the demo from the README.

Weeks 9–10: Optional stretch

only if weeks 1–8 are solid
  • One state’s RERA delay lookup for a project name
  • A “paste a listing URL” page
  • A second portal parser

If you get stuck

  • Shrink the problem: test one function with one fixture before touching the browser.
  • Use the console and chrome://extensions error view; most extension bugs show up there.
  • Time-box a bug to 45 minutes, then write down what you tried and ask for help.
  • Behind schedule? Cut Week 9–10 first, then the optional model; never cut evaluation or the threat model.

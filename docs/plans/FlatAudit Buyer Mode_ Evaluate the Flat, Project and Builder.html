Buyer mode: evaluate the flat, the project and the builder

Extend FlatAudit from “is this listing suspicious?” to “what do the official records say about this home and who is building it?”. Facts with sources, never a verdict.

0% complete

What buyer mode evaluates

1. The flat

  • Price and price per sq ft vs peers, same area type only
  • Carpet vs super built-up, floor, age, possession status
  • Duplicate photos, token-to-hold phrasing
  • Total cost of ownership

2. The project

  • RERA registration number shown or missing
  • Declared vs revised completion date
  • Progress updates, declared litigation, escrow bank
  • Status: new launch, under construction, completed

3. The builder

  • Past projects the promoter disclosed
  • How often dates were revised
  • Complaints or litigation fields where the portal shows them
  • Data completeness for each fact

4. Paperwork and cost

  • Documents to ask for, by scenario (resale or new)
  • Stamp duty and registration estimate
  • Hidden costs and EMI with the user’s own inputs
  • A “verify with a lawyer” handoff

What the output looks like

Flat✓ Price per sq ft is near the typical range for 18 similar listings (carpet area basis)
Project⚠ Completion date was revised once, from the original date; see the official page
Builder? Disclosed past projects found: 6. Complaint data: not shown by this portal
Paperwork? Not verified by this tool: title, encumbrance, approvals. Checklist below

Illustrative only. Every line carries a source link, a “data as of” date, and a note on what is not covered. There is no overall score or “safe / unsafe” label.

What official sources can give you

  • State RERA portals generally publish project registration details, promoter information including past projects, declared completion dates, progress updates and, in some states, litigation and complaint information.
  • Fields, coverage and layout differ by state and change over time, so each state needs its own reader and its own fixtures.
  • RERA does not cover every property, and a registration number is not a guarantee of quality or legality.
  • Third-party sites mirror RERA data. Prefer the official portal as the source and link to it.

Key by RERA number, not by builder name. Builders often register projects through separate companies or LLPs, and names are spelled many ways. Use the RERA number as the join key; offer name matches only as suggestions with a confidence note.

Builder fact sheet (facts only)

Show

  • Projects the promoter disclosed, with status
  • “Dates revised in 3 of 8 projects with both dates available”
  • Average revision length, when both dates exist
  • Litigation field as declared, and complaint counts if the portal shows them
  • Data completeness: how many fields were found

Avoid

  • “Reliable”, “risky”, “bad builder”, or any score
  • Treating “nothing found” as “no problems”
  • Guessing links between companies
  • Using wording that isn’t on the official page
  • Mixing different states’ fields as if identical

Plan (about 10–12 weeks)

0. Decisions and wording

2–3 days
  • Pick one pilot state and city, and read its RERA portal terms and project page layout
  • Write a wording guide: allowed phrases, banned phrases, mandatory caveats
  • Define the rule: no overall verdict, every fact has a source and date
Done when: the pilot and the wording rules are written down.

1. Link listing to project

about 1 week
  • Parse RERA ID, builder and project name from sale listings; handle “not shown”
  • Add a manual field where the user can paste a RERA ID
  • Button to the official state search with the ID pre-filled where possible
  • Basic format sanity check only; never claim an ID is valid from format alone
Done when: a buyer reaches the official project page in one click.

2. RERA project reader (one state)

about 2 weeks
  • Save 10 official project pages from your pilot state as sanitized fixtures
  • Define ProjectFacts: registration number, status, promoter, original and revised completion, litigation field, progress, escrow bank
  • Content script reads the page the user opened and stores facts locally
  • Health test: report which fields were found; flag layout changes
  • Measure field-level accuracy against the page, checked by hand
Done when: at least 95% of key fields match the official page across your fixtures.

3. Builder fact sheet

1–2 weeks
  • Parse the promoter’s disclosed past-project list when the user opens it
  • Compute revision statistics only where both dates exist; show the denominator
  • Handle multiple entities with a “not confirmed to be the same builder” note
  • Pilot data file for about 20 projects with source URL and date
Done when: the sheet shows counts, denominators and sources, and never a judgment.

4. Flat evaluation and cost

about 2 weeks
  • Sale benchmarks per BHK, property type, status and area type, using the existing ladder
  • Cost estimator: base price, stamp duty and registration, GST where applicable, maintenance, parking, other charges
  • Put state rates in an editable data file with source and date; label results indicative
  • EMI calculator with the user’s own rate, tenure and down payment
Done when: the user sees an all-in cost range and can change every assumption.

5. Paperwork checklist and report

1–2 weeks
  • Scenario checklists: resale, under construction, ready from builder
  • Items to ask for, such as registration certificate, approved plans, completion or occupancy documents, encumbrance record, tax receipts and society documents; mark state-specific items
  • One-page buyer report with ✓ / ⚠ / ? lines, sources and dates; print or save locally
  • Clear notice: not legal or financial advice; does not verify title
Done when: a buyer can print one page and take it to a lawyer.

6. Validate

about 2 weeks
  • Check 10–15 real projects by hand against the official portal; report field accuracy and link success rate
  • Test with 3–5 people researching a purchase; ask what they understood and what they would do next
  • Ask someone knowledgeable in real estate or law to review the wording and checklist
  • Update the threat model and privacy policy, then publish a new version
Done when: you can state measured accuracy and show what real users did with the report.

How you’ll measure it

  • Extraction accuracy: share of key fields that match the official page.
  • Linking success: share of listings that reach the correct project.
  • Coverage honesty: share of facts shown with a source and date, and how often “not found” is reported correctly.
  • Usefulness: whether testers can say what to verify next after reading the report.

Risks

Defamation and over-trust: builder information is sensitive. Show only what the official page says, link to it, and avoid evaluative words.
State differences: each state portal has its own layout and fields. Expect one reader per state and regular breakage.
Wrong entity: linking a listing to the wrong project or builder is worse than showing nothing. Prefer the RERA number and ask the user to confirm.
Portal terms and blocking: keep reads user-driven, avoid automation against CAPTCHAs, and check each portal’s terms.

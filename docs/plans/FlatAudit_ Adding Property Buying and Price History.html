Where v1.0 really stands

  • 30 listings is a smoke test, not a metric. Even a perfect 30 out of 30 is statistically consistent with a true error rate of up to about 10% (the “rule of three”). Keep the figure, but describe it as an early check and keep growing the set toward 150+ across more cities.
  • “People test it” isn’t done yet. Feedback buttons are built, but no one has used it for a week. Until then, treat the tag as a release candidate in your own mind, and in the README if you like.
  • Not yet confirmed: behavior on live, current portal pages, and the deployed backend. Check both before adding a whole new product area.

Why you can’t extract a property’s price history

  • A page shows only today. The extension reads the current price. Portals rarely publish a per-listing price timeline.
  • Your tracker starts at first sight. It records snapshots from the moment a user views or tracks a listing, so the past is empty by design.
  • Past data lives elsewhere or nowhere. It is held by the portal, in government records, or in archives, and each has access limits.
  • Crowd data needs time and users. Aggregates only become useful after many people have contributed.
Reframe: “price history” for buying can mean five different things. Build the ones you can get honestly, label each by source, and never fabricate a past.

Scope the buying pilot

One city, one portal, one type first: resale, ready-to-move apartments. Add under-construction projects and other cities only after that works. Buying is high stakes and infrequent, so a narrow, correct slice beats a broad, shaky one.

1. Sale-listing foundation

about 1 week
  • Add listingType: "rent" | "sale" across parsers, tracker, API and packs
  • Parse sale price in ₹, Lakh and Cr; price per sq ft; area type; possession status; RERA ID if shown; builder and project
  • Pick one portal and save sanitized sale-listing fixtures from your pilot city
  • Extend the health check: fail on empty price, area or locality for sale pages
Done when: sale pages on the pilot portal parse correctly and rent behavior is unchanged.

2. The price history you can actually build

about 2 weeks
  • Generalize the tracker to sale prices; show change since first seen and time on market
  • Parse any trend or price-drop elements the portal shows, labeled as “shown by the portal”
  • Backend: store daily sale observations and detect reposts by photo hashes and area
  • Experiment: check whether the Internet Archive has useful earlier snapshots; keep it only if coverage is decent
  • Label every history item with its source and start date in the UI
Done when: a tracked sale listing shows a clear, honestly labeled timeline with no invented data.

3. Sale benchmarks

about 2 weeks
  • Reuse the fallback ladder with packs keyed by cell, BHK, property type and status
  • Compare price per sq ft using the same area type only
  • Raise minimum sample sizes for sale; show “not enough local data” more readily
  • Add a monthly trend per cell once you have weeks of data
Done when: every price verdict shows its level, sample size and area type.

4. Buying-specific checks

about 2 weeks
  • RERA: show whether an ID appears; link out to the state’s official RERA search rather than scraping it
  • Add a per-state reference-value data file with source and date for your pilot state, kept separate from market prices
  • Sale-specific phrase rules, such as paying a token to “hold” a flat or unusual owner stories
  • Keep duplicate-photo logic softened for builder renderings, as you already do
  • Use neutral wording for builders and projects: show public facts, never reputational labels
Done when: each check states what it found, where it came from, and what it cannot tell you.

5. Buyer experience

about 1–2 weeks
  • Sale compare view: price, price per sq ft, possession, RERA shown, maintenance, floor, age
  • A short “before you pay” checklist that points users to a lawyer and official records
  • Optional: a simple EMI calculator using the user’s own inputs
  • A visible note: this is not legal or financial advice and does not verify title
Done when: a test buyer can shortlist three homes and knows what to verify next.

6. Validate before you announce

about 2 weeks
  • Label 100+ real sale listings across at least 3 cities; report precision, recall and false positives
  • Test with people actually house-hunting; ask whether verdicts matched their judgment
  • Update threat model and privacy policy for sale data and the new data files
  • Tag a new release only after these checks
Done when: sale features have their own measured results and real-user feedback.

Guardrails for high-stakes buying

Do

  • Show source, date and sample size on every number
  • Say “not enough data” when that’s true
  • Link to official records instead of copying them
  • Tell users what the tool does not check

Don’t

  • Say a home is “safe”, “legal” or “a good investment”
  • Label a builder or seller as untrustworthy
  • Present reference values as market prices
  • Backfill history you can’t source

Risks

Over-trust: a “fair price” badge may be treated as financial advice. Use ranges and plain caveats, not a single approval.
Thin data: sales listings are fewer and more varied than rentals. Expect many “not enough data” results at first.
Scope creep: title checks, loan eligibility and legal review are different products. Link out instead.
Data terms: read each data source’s terms before using it, especially government and archive data.

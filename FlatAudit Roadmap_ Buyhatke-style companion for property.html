FlatAudit roadmap: a Buyhatke-style companion for property

From “is this listing suspicious?” to “which listing should I pick, what did it cost before, and where else is it listed?” Planned to stay small enough for one person to finish and safe enough to publish.

Principles that keep it practical

Do

  • Local-first: history lives in the browser; the server is optional
  • Read only pages the user opens or saves
  • Share aggregates (medians, counts), never raw listings or contacts
  • Go deep on one portal, then widen
  • Keep every number explainable

Don’t

  • Run server-side crawlers of portals
  • Republish listing text, photos or phone numbers
  • Show a “fraud” verdict on a named person
  • Add permissions without updating the threat model
  • Chase every city before one city is accurate

Phases

Phase 0: Make the foundation honest

about 1 week
  • Hand-label 100+ real listings you opened yourself (private file, not committed)
  • Make evaluate.py call the real signals.js (via a small Node script) or share one JSON rules file
  • Re-run metrics on real data; report precision and recall plus the false positives you found
  • Label the synthetic set clearly as “synthetic, for unit tests only” in the README
  • Replace guessed benchmarks with medians from your real labels, with sample sizes shown
Done when: the README reports metrics on real listings and says how many.

Phase 1: Watchlist and price history

2–3 weeks · the Buyhatke core
  • Parse a stable listing key per portal (portal + listing ID from the URL) and canonicalize URLs
  • Add a “Track” button in the badge; store snapshots {t, rent, deposit, status} in chrome.storage.local
  • Record a new snapshot only when something changed or 24h passed
  • Draw the history as an inline SVG sparkline (no chart library)
  • Popup page: list of tracked listings with current rent and change since first seen
  • Alerts on revisit first (“rent changed since you last saw it”)
  • Optional, opt-in: a slow background re-check of only the listings the user tracks, using chrome.alarms with long, randomized gaps and a low cap
Done when: you track 3 real listings, revisit them over several days, and the history and change notices are correct.

Phase 2: Shortlist and compare

about 2 weeks
  • Compare view for 2–4 tracked listings: rent, deposit multiple, area, rent per sq ft, floor, signals fired
  • Highlight the best value in each row; keep a user note per listing
  • Status tags: Interested, Visited, Rejected; export the shortlist as CSV
  • Add “time on market” from your first-seen date, labeled as “first seen by you”
Done when: a friend can choose between three flats using only the compare view.

Phase 3: “Also listed on…” matching

2–3 weeks · the clever part
  • Extend the backend: store listing key, portal, area, floor and up to 3 image hashes per observation
  • Write a match score: image hash within a small distance (strong), same locality and BHK, rent within about 5%, area within about 3%, same floor
  • Require at least two independent signals; show “likely the same property”, never “the same”
  • Label 30+ true and false pairs by hand and measure match precision
  • UI: “Also seen on Portal B at ₹X” with the user’s own link, not stored third-party content
Done when: match precision on your labeled pairs is reported and wrong matches are understood.

Phase 4: Real market insight from crowd data

about 2 weeks
  • Compute locality medians from observations, trimmed for outliers, and show only when the sample is large enough (for example, 10 or more)
  • Fall back to broader area, then to city baseline, and show which level you used
  • Add rent per sq ft and deposit multiple vs local median with a plain verdict (“below / typical / above”)
  • Detect reposts: same hashes and area reappearing under new listing IDs
  • Deduplicate by listing key so one user refreshing cannot skew medians
Done when: no verdict is shown without a visible sample size.

Phase 5: Reach real users safely

about 2 weeks
  • Update the threat model for new permissions (storage, alarms, notifications) and justify each
  • Write a plain-language privacy policy; keep telemetry off by default and opt-in
  • Read each supported portal’s Terms of Service and note limits in the README
  • Add a selector health check: a test that fails loudly when a parser returns empty fields
  • User-test with 5–10 people looking for a flat; fix what confuses them
  • Publish to the Chrome Web Store as unlisted first; deploy the backend on a free tier
Done when: 5 real people use it for a week and you have their feedback written down.

Stretch

only after phase 5
  • Phone use: check whether Firefox for Android supports your extension; or add a “paste a link” web page
  • Buying side: price per sq ft and a RERA project lookup for one state
  • Edge and Firefox ports; localization (Hindi labels)

Risks and guardrails

Portal Terms and blocking: a widely used extension that reads portal pages can attract blocks or notices. Keep it user-driven, rate-limited and aggregate-only, and don’t claim legal safety you haven’t checked.
Cold start: medians and cross-portal matches are weak until many people contribute. Make the local watchlist useful on its own so value doesn’t depend on the crowd.
Selector breakage: every portal redesign breaks a parser. Prefer one portal done well, with fixtures refreshed from real pages.
Wrong matches and false alarms: show confidence and reasons; let users hide a signal they disagree with.

How to know it works

  • Portfolio: precision and recall on real listings; match precision on labeled pairs; a clear “limits” section.
  • Usage: tracked listings per user, revisits, and how often alerts lead to action.
  • Trust: zero stored personal data, verified by a test that inspects every API payload.

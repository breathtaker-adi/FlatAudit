Every-city benchmarks without hardcoding

How FlatAudit can judge rent and deposit fairly in any Indian city: learn from data, say how sure you are, and stay silent when you don’t know.

0% complete

Still open from Phase 0: the 97.3% accuracy and 95.1% precision are measured on the synthetic dataset, so they show the rules behave as designed, not that they work on real listings. Hand-label real listings from several cities before quoting any metric.

The short answer

  • Stop storing absolute numbers per city. Replace LOCALITY_BENCHMARKS with a function that returns {median, n, level, confidence} from data, and judge listings relative to their peers.
  • Use the page itself as the first data source. On a search-results page the extension already sees dozens of comparable listings for that locality. Computing a median from them locally works in every city on day one, with no server.
  • Key places by coordinates, not by names. A geohash prefix gives an automatic hierarchy (area → district → city) and ignores spelling differences like “Indiranagar” vs “Indira Nagar”.
  • Fall back step by step (local → area → city → tier) and show which level was used. If there isn’t enough data, show “not enough local data” instead of a verdict.
  • Ship data, not code. The backend publishes small, static “market packs” of aggregates; the extension caches them. Chrome allows remote data, not remote code.

Data quality rules

Keep the benchmark clean

  • Exclude listings that fired price or advance-fee signals; bait prices would drag the median down
  • Use median and MAD, with trimming; a robust z-score is (x − median) / (1.4826 × MAD)
  • Compare rent per sq ft when area is known
  • Separate furnished, semi- and unfurnished
  • Separate flats, independent houses, PG and shared rooms
  • Use a rolling 60–90 day window and warn when a pack is stale

Keep it fair

  • Judge by ratio to peers (for example, under 0.6× the median), tuned per tier, not by fixed rupees
  • Learn deposit norms per city from data; use a broad default range when unknown
  • Never show a verdict without its sample size
  • Treat weak data as “unknown”, not “normal”
  • Count a listing once per day, so refreshes don’t skew medians

Where seed data can come from

  • Your own users and testers: the safest and most relevant source, but slow at first.
  • Peer-page data: immediate and local, as described above.
  • Public datasets: government housing price indices cover sale prices in a limited set of cities, and open rental datasets are patchy. I haven’t verified current options, so check each source’s license and coverage before using it.
  • Avoid: bulk scraping portals to fill a database, which carries the same Terms of Service and blocking risks as before.

Risks

Thin data in small cities: the ladder will often end at “not enough data”. That is correct behavior; say so honestly rather than guessing.
Biased samples: peer pages reflect the search filters and crowd data reflects who installed the extension. Show sample size and level every time.
Poisoned data: someone could submit fake observations. Dedupe per listing per day, cap each contributor’s weight, and use robust statistics.
Parser coverage: portals mostly use one layout across cities, but local sections and units vary. Test fixtures per city.

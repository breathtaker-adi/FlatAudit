Listing Trust Analyzer

A privacy-preserving browser extension and small API that flags scam-pattern signals on Indian rental listings and explains each flag. Built as a cybersecurity portfolio project, not a business.

Problem

  • Rental portals reward listing volume, so bait listings, duplicated photos and broker “fishing” ads are common.
  • Renters lose time, share their phone numbers, and sometimes lose money to UPI advance-fee scams.
  • Users get no cross-checking help while browsing; reporting buttons are slow and passive.
Honest note: the original report’s claims (for example, “up to half of listings are phantom”) were unsourced. This project’s first job is to measure the problem on real listings, not assume it.

Goal and scope

Goal

  • Build a working, well-engineered detection tool
  • Evaluate it honestly on labeled data
  • Threat-model it like a security product
  • Publish code and a write-up

Not a goal

  • Revenue, paid dossiers, B2B APIs
  • Covering every portal or city
  • Naming or accusing individuals
  • Bulk crawling of portals

What it does

On a listing page the user is already viewing, the extension computes signals locally and shows a badge with plain-language reasons (“why flagged”) instead of an opaque score.

SignalHow it worksWatch out for
Duplicate image64-bit dHash computed in the browser; compared against hashes already seenLegitimate brokers reuse photos of the same flat, so “seen in several places” is a hint, not proof
Price outlierz-score against similar listings in the same locality and BHKNeeds enough data per area; start with a few localities
Deposit ratioDeposit divided by rent, compared with local normsNorms differ by city; check them per market
Scam phrasesRules for advance-fee wording (army transfer, key courier, token before visit)Keep the list small and reviewed against real examples
Posting velocityListings per hashed contact token per week, if visible on pages the user opensLikely sparse; optional
Output rule: every badge states an observable fact (“this photo appeared in 4 other listings”). The UI never says “scammer”, “fraud” or “criminal”. Labels: Looks normal Some signals Many signals

   ▼
FastAPI backend ── SQLite/Postgres
   │  stores: image hash, price, area, BHK   (no photos, no phone numbers)
   ▼
Signals + “why flagged” → badge in the page
  • Extension: TypeScript, Manifest V3, MutationObserver for dynamic pages.
  • Backend: FastAPI with a simple hash lookup (linear or BK-tree later); a small database.
  • Selectors: prefer semantic attributes and structure over generated CSS class names.

Evaluation plan

  • Hand-label about 250 listings as suspicious or normal, with a one-line reason each.
  • Report precision, recall and the false positives you found, such as legitimate duplicate photos.
  • Compare simple rules against any model you add; keep a model only if it beats the rules on held-out labels.
  • Keep the dataset private or anonymized.

Security and privacy

Threat model the tool itself

  • Minimal permissions, strict CSP, no remote code
  • Untrusted page data: sanitize everything read from the DOM
  • API abuse: rate limits and input validation
  • Walk through STRIDE and document it

Privacy by design

  • Analyze only the page the user is viewing
  • Store hashes, not images
  • No phone numbers or personal data stored
  • Respect portal Terms of Service: no bulk or evasive crawling

Roadmap (about 10 weeks, solo)

  1. Weeks 1–2: skeletonParse listing cards on one portal, compute dHash locally, show a basic badge.
  2. Weeks 3–4: signalsAdd price z-score, deposit ratio and phrase rules; stand up the small backend.

Risks

Portal changes: page layouts change often. Keep parsers small and isolated, and support one portal well.
Too few labels: if fewer than about 100 listings can be labeled, narrow the scope or report results as exploratory.
Over-claiming: flags are signals, not verdicts. State limits and false positives in the README.

First step

Collect and screenshot about 30 listings (15 suspicious, 15 normal) into a spreadsheet with price, deposit and the reason you flagged each. This defines the signals before any code.
